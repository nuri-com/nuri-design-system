## The finding — `npm install` collapses the dual-version RN tree; the lockfile is a mechanical rename

`npm install` (and `npm install --package-lock-only`) on npm 10.8.2 **deterministically COLLAPSES the deliberately-retained dual-version react-native tree** (root `0.80.3` → `0.81.5`; ~356/1823-line lockfile churn) — the orphaned root hoist [`jest.config.js`](../packages/rn/jest.config.js) + the [N+19-M4 retro](./N+19-M4.md) document is kept by npm's *conservative* re-dedupe and whose collapse is **"out of scope · don't-force-it"** (a from-scratch regen was explicitly **rejected** at M4). A pure rename must not carry that mutation. Since only `package-lock.json` is committed (CI's `npm ci` rebuilds the tree from it), the fix is a **mechanical `factory`→`rn` string rename on the committed lockfile**: all 48 refs are the workspace/path (`packages/factory/node_modules/*` is the 0.81.5 half of the dual tree) — **no unrelated `factory` dependency** — so every resolution/version/integrity hash is preserved. Result: **48/48 balanced diff**, dual tree intact (`0.80.3` lines: 29 → 29), and **`npm ci` rebuilds root-`0.80.3` + nested-`0.81.5` exactly**. (Operator-confirmed at the checkpoint over the alternative — accept npm's collapse.) This is the lockfile equivalent of the `git mv`; it deviates from the brief's "`npm install` regenerates / don't hand-edit" only because npm's regen over-reaches.
