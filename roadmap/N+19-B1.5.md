## Verdict — the model HELD

All three recipes — **Button** (interactive · 3 variants × 3 sizes + states), **IconAvatar** (static ·
4 variants), **Topbar** (open layout · title-bar + centered) — compose to **pixel-parity** with the live
components using **only** the primitive namespaces, with **zero raw style** outside a small, closed,
**additive** set of LOGGED gaps. The gaps are exactly the primitive extensions B2 will ship; **none
requires redesigning 65.3.** The model's central claims are confirmed in the browser:

- **Recipe = pure namespace composition.** Every box/layout/colour/font property of every recipe is
  reproduced from `stack` · `box` · `typography` · `palette` + the `interactive`-derived patches.
  Computed-style diff live-vs-composed = **IDENTICAL** across the matrix (box geometry, **bg, fg**, font;
  topbar host + pivot).
- **Namespaces are disjoint (§6) — and box owns NO colour.** `box` (geometry) + `stack` (flex) rule-sets
  co-exist on one node with **no property collision**. All colour is `palette`, applied independently —
  so a node can carry both without conflict (validating the RN single-`<View style>` shape).
- **Colour flows by scope (F-BOX-FG-1).** Set the role `fg` on the root; text/icon inherit via
  `currentColor`. Verified: solid glyph/label = `on-solid`; soft/ghost/canvas = ambient `text-primary`;
  subtle = `border-strong`. A `variant` patch touches **root only**.
- **The pivot's `flex:1` is anatomy.** Topbar's content pivot, reproduced as `stack.fill='grow-shrink'`
  (`flex:1 1 auto; min-inline-size:0`), pushes trailing to the row end by construction — matches the live
  pivot exactly.

### How it was validated (evidence)

The page renders each recipe twice — the shipped component (`live`) beside the namespace composition
(`composed`) — across variants / sizes / states, on the fixed light + cream + lilac playground surface
(decision 57). Validated three ways in the preview browser:

1. **Visual** — composed indistinguishable from live in every cell.
2. **Computed style** — `getComputedStyle` diff on the painting nodes (box geometry · padding · radius ·
   **background · colour** · flex · the label/title fonts · topbar host + pivot): **IDENTICAL** for all
   18 composed roots. `display` also matches (`live[flex] comp[flex]`) and **widths are equal** — both the
   live `inline-flex` button and the composed `flex` div are *blockified* in the flex parent (see §4.5).
3. **Zero-raw-style audit** — enumerated every inline-style declaration on all 18 composed roots: **every
   one is a LOGGED gap** (the 10 properties in §5); `offenders: []`; **`box.background` used 0×** (box
   carries no colour · §4.3).

§9's "**built** (live consumers)" means *the token/value has a live consumer*, **not** *the primitive

| Extension | CSS realized | Consumers | Note |

### `palette` — the biggest build (no primitive today · §4.4)
There is **no palette element**. The prototype realizes **all** colour inline (LOGGED) — bg, fg, pressed,
fg-only roles, chrome — plus scope inheritance where the role fg = ambient `text-primary`. B2 builds the

| Role / case | CSS realized | Consumer |
|---|---|---|
| `solid` | `background: accent-solid` + `color: on-solid` | Button, IconAvatar |
| `soft` | `background: bg-strong` (fg via scope) | Button, IconAvatar |
| `ghost` | transparent (fg via scope) | Button, IconAvatar |
| `subtle` (fg-only) | `color: border-strong` | IconAvatar |

| **chrome** (`canvas \| subtle \| strong`) | `background: bg-canvas` (fg via scope) | Topbar |

### `interactive` (no primitive — factory + the box/palette patches above)
A cross-cutting **flag**. When set it wires: `Pressable`/native-button + `cursor` + `transition`
(affordance), the `:active` **pressed colour** (→ palette), the `:active` **scale** (→ box.transform),
the **disabled opacity** (→ box.opacity), the **focus ring** (`:focus-visible outline`). The prototype
could only **simulate** pressed/disabled **statically** (no `:active`, no Pressable) — confirming
`interactive` is a realization concern whose *outputs* are the box/palette extensions above.

## 4 · Model strains (surfaced · two resolved with the operator at the checkpoint)

### 4.1 · anatomy-vs-default — the fuzzy line inside `structure.base`
`Descriptor.structure = { anatomy, base }` reads *"anatomy (invariant) + base (defaults / locked)"* — but
**`base` mixes two kinds** with no marker:
- **load-bearing / invariant** — Topbar height `size-lg`, the pivot's `flex:1 1 auto`+`min-inline-size:0`.
  Changing these **breaks** the recipe (the pivot stops pushing trailing). Confirmed anatomy.
- **overridable default** — Topbar `gap:sm`, `paddingStart/End:lg` (the latter is *literally* the `inset`
  override knob · decision 46/64). A consumer is meant to change these.

Both sit in `structure.base`. For the **closed recipe** the distinction is moot (all locked). For the
**open `composition-` primitive** (§7 · 64.1) it matters (which base values are knobs vs fixed?). The same
`stack{row,center,center}` is an *overridable default* on `composition-button` and *locked* on the
`button` recipe — identical data, only the layer's openness differs (§7 says exactly this; the prototype
confirms openness is **not** a render property — both render identically). **Surface**: the open-primitive
layer would benefit from `base` distinguishing load-bearing-locked from overridable-default. Minor;
doesn't block B2's recipe (closed) emit.

### 4.2 · web multi-primitive merge-vs-nest (+ the `display:contents` wrapper)
A model node carries several namespaces (Button root = stack ⊕ box ⊕ palette ⊕ interactive). On **RN** that
is **one** `<View style={{…}}>`. On **web** each primitive is a **separate custom element**, so a
multi-namespace node must **nest** (`<nuri-box><nuri-stack>…`) — *or* merge at the underlying **class**
layer (`class="nuri-box nuri-stack" data-*`). Two findings:
- ✅ **the merge works** — namespaces disjoint (§6 · box no colour · §4.3), so the rule-sets co-exist with
  no collision. The web **can** realize the single-node model — just not through the element-per-primitive
  API. The prototype composes at the class+data-attr layer = the faithful web analogue of RN's merged
  `<View>`.
- 🔎 **NEW · the wrapper blocks inline augmentation.** Each `<nuri-*>` is `display:contents` with the
  painting node created in JS — so (a) two wrappers can't share an element, **and** (b) a wrapper cannot
  be inline-styled (`<nuri-box style="min-height:…">` is dropped). So the gap-reproduction **must** drop
  to the class layer (the only place gaps co-locate with the merged namespaces).

**Implication for B2**: the web **factory** emits **one painting node per anatomy node** carrying the
merged namespace classes/styles (NOT nested wrappers) — mirroring RN's single `<View>`. The
element-per-primitive API is for hand-authoring; the factory-emitted recipe is class/style-merged.

### 4.3 · ✅ RESOLVED (operator) · `box` owns no colour — `box.background` ≠ palette
65.3 §6 puts all colour on `palette` and resolves **`backgroundColor → palette` (not box)**. But decision
42 gave Box a `background` prop (5-enum incl. chrome + accent surfaces). **Operator decision at the
checkpoint: box must NOT carry a background — otherwise composing `box` + `palette` collides** (two
namespaces emitting `background` breaks §6 disjointness). So:
- **The model rule stands, unambiguously**: `box` = geometry only (sizing · padding · radii · transform ·
  opacity); **`palette` owns every colour** (bg, fg, pressed, fg-only, chrome). The prototype is built
  this way — palette applied **inline** (no primitive · §4.4), `box.background` used **0×** (audited).
- **chrome** (`canvas | subtle | strong`) is therefore a **`palette` slot**, not `box.background` — bg-only
  (no fg/pressed), fg via scope. Confirmed on Topbar (`chrome=canvas`).
- **Follow-on (flag · not this session)**: decision 42's shipped `box.background` is **superseded for
  composition**. Whether to deprecate/remove the Box prop is a separate Box-API migration — it has live
  consumers (e.g. Tabs' `<nuri-box background="strong">`) — to scope when `palette` lands (B2 / P11).

### 4.4 · `palette` has no primitive (the deepest)
Four namespaces have a web element — `stack`, `box`, `typography`, the glyph leaf (`<nuri-icon>`).
**`palette` has none.** With box.background removed (§4.3), the prototype realizes **all** colour inline
(13× `background`, 7× `color`) + scope inheritance for ambient fg. It is the **least-served** namespace and
the single biggest B2 build (the `{variant,accent,muted,interactive} → {bg,fg,fgMuted,border,pressed}`
engine of §2). Until it exists, every recipe's colour is inline-LOGGED — which is precisely what the
prototype demonstrates, and where most gaps now land.

### 4.5 · ✅ RESOLVED (operator) · inline-vs-block **dissolves** — RN is flex-only
A first pass needed `display:inline-flex` to make Button/IconAvatar content-width (vs Topbar's full-width
block). §6's stack knobs have no display-mode knob, so this looked like a new extension. **It is not.**
- **RN has no inline/block.** RN layout is flex-only (Yoga): `display` is `'flex'` (default · `flexDirection:
  'column'`) or `'none'`; no `block`/`inline`/`inline-block`/`inline-flex`. Only `<Text>` flows inline.
- **Empirical (measured in-browser)** — composed `block-flex` vs `inline-flex`, same box props:

  | parent context | block-flex | inline-flex |
  |---|---|---|
  | flex column `align-items:stretch` | **300** | **300** |
  | flex column `align-items:center` | **64** | **64** |
  | plain block parent (web normal flow) | 300 (fills) | 64 (content) |

  They differ **only** in a plain block parent — web normal flow, which **has no RN analogue**. In any
  flex parent a flex item's display is *blockified*, so width = the parent's `align-items` + the item's
  `flex-grow`, identical for both.
- **Resolution**: **no stack `inline` knob, no factory rule.** Recipes live inside stacks (flex parents) —
  the RN-parity invariant — so a plain `flex` root behaves exactly like RN. The prototype now uses plain
  flex roots (no `inline-flex`); the harness places specimens in a flex context, and live ≡ composed:
  both compute `display:flex` (the live `inline-flex` is blockified) at **equal widths** across all 11
  button cells. The `inline-flex` in the first pass was a harness artifact, not a recipe concern.

### 4.6 · NEW · minor · label/title font lives on the part, not the root
The live Button carries the label font on the **root** box (the label is a bare text node). The model puts
it on the **`label` part** (`label.typography`). Both render identically (verified: composed
`<nuri-typography>` label font === live root font). The model's part-based font is **faithful** — the
web's root-font is an accident of the single-node button; the factory should emit font on the **label
part** (as `button.tsx` / Topbar's pivot already do · decision 64). No visual strain; noted for the factory.
