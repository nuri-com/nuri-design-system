## Decisions locked

- **[Decision 48](../decisionlog.md#48-typed-buildiconsts-emit--svgxml-over-the-shared-registry--one-registry-two-readers--n68) ·
  Typed `build/icons.ts` emit · SvgXml over the shared registry · one
  registry, two readers.** (a) A *typed* emit (not inline-on-RN like
  the web) gives the RN runtime an `IconName` union — a bad key is a
  compile error, not a runtime warn — while `icons.js` stays the SSOT;

  `SvgXml` over the path string, **not** SVGR / per-glyph `<Path>`
  codegen — codegen would fork the glyph source into a second

  rests on. (c) No `react-native-svg` dependency — local type shim
  only; the migration test proves the prop *contract*, never renders.
  Anti-scope: no new glyphs (stays 17 × 3), `icons.js` untouched, web
  `<nuri-icon>` untouched, no expanded prop surface, no partial
  renderer. `build/icons.ts` is generated, never hand-edited
  ([decision 35](../decisionlog.md#35-pipeline-sources-vs-build-outputs-physically-separated--pipeline-source-build-generated-only--n604)).

## Why a typed emit, not inline-on-RN like the web

The web inlines `icons.js` directly (zero-build). RN has no equivalent
zero-build inline and benefits from a **typed** `IconName` union so a
bad key fails at compile, not runtime. Emitting the registry once as
`build/icons.ts` gives the RN runtime a typed reader while keeping
`icons.js` the single source of truth. The byte-stable drift guard
(on-disk emit === `emitIconsTs(ICONS)`) makes the single-source
invariant machine-checkable.

## Why SvgXml over the path string, not SVGR / per-glyph codegen

SVGR or hand-authored per-glyph `<Path>` components would fork the
glyph source into a **second hand-maintained shape**, breaking the
single-registry invariant decision 38 rests on. Feeding the registry's
verbatim SVG string to `SvgXml` keeps exactly one authored copy of each
path. Icons are a closed enum of named SVG assets the CSS cascade can't
express — a verbatim typed mirror is the right emit.

## Why no react-native-svg dependency

A spec repo with no RN build gains nothing from pulling an RN runtime
package in. The local type shim declares only the `SvgXml` surface the
Icon consumes, so `tsc` resolves the import and the migration test
proves the **prop contract** typechecks against the shared registry.
When a real RN build lands: delete the shim, add the package — the Icon
is written against that exact prop surface, so the swap is mechanical.

## Why N+6.8 (a bridge, not N+7)

Four sessions kept the Icon funnel narrow (IconButton the single
consumer) while deferring the renderer — a deliberate "pay down the
debt once the shape is maximally concrete" stance. N+6.8 is that
payment: the highest-leverage RN-side debt, closed without growing the
web surface, the token set, or the glyph count. It clears the runway so
the next direct-Icon consumer (or the first real RN build) inherits a
working glyph path rather than a stub.
