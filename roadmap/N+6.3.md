# Session N+6.3 · Iconography · `<nuri-icon>` over a 17-glyph phosphor registry

**Status**: closed (2026-05-29)
**Type**: main sequence (the iconography foundation that unlocks
icon-consuming components — IconButton at N+6.4, then
SegmentedControl / ListItem / TabBar)

## Outcome

Nuri ships its first **visual atom**. **Icon**
([`lib/components/icon/`](../lib/components/icon/)) lands as
`<nuri-icon name size fill>` — a thin Nuri facade over a
hand-curated registry
([`icons.js`](../lib/components/icon/icons.js)) of 17 phosphor
glyph keys × 3 weights (51 SVG path strings) under
[decision 38](../decisionlog.md#38-icon-component--phosphor-source--nuri-icon-name-nuri-facade--2-size--fill--registry-based-js-dispatch--n63).

The session establishes **registry-based JS dispatch** as the
canonical shape for components whose vocabulary is an enum of named
assets the CSS cascade can't select on — the sibling co-pattern to
[decision 37](../decisionlog.md#37-layout-primitives-consume-semantic-vocabulary-via-prop--no-component-token-aliasing--n62)'s
attribute-dispatch. Same prop-mirroring discipline (`size` →
`data-size` for CSS box dimensions), different resolution mechanism
(`name` → registry lookup → inline SVG in JS).

API · operator-locked at session open:

```
<nuri-icon
  name   (required)   registry key · kebab-case · warns [NuriIcon] unknown name "<value>"
  size   "md" | "sm"  default "md"
  fill   boolean      presence forces the fill weight
>
```

Weight is **coupled, not a prop** (md→regular · sm→bold ·
any+fill→fill) — Nuri never exposes phosphor's raw weight set.
Colour is **`currentColor` only** — no tone/accent/color prop; the
icon inherits its parent's text colour like a glyph in running
text. Size reuses the existing `--nuri-size-*` semantic vocabulary
as a 2-leaf subset (md → `--nuri-size-sm` = 28px, sm →
`--nuri-size-xs` = 18px); **no new `--nuri-icon-size-*` family** — a
`--nuri-icon-size-md: var(--nuri-size-sm)` alias would be the
"useless indirection" decision 37 already rejects.

## Decisions locked

- **[Decision 38](../decisionlog.md#38-icon-component--phosphor-source--nuri-icon-name-nuri-facade--2-size--fill--registry-based-js-dispatch--n63) ·
  Icon component · phosphor source · registry-based JS dispatch.**
  `<nuri-icon name>` inlines an SVG path string keyed by `name`
  from a hand-curated registry. Weight coupled to size+fill (not a
  raw prop); colour `currentColor` only; size is a 2-leaf subset of
  semantic `--nuri-size-*` dispatched via `data-size` attribute
  selector. Empty `@layer tokens` → rides decision 37's empty-emit
  branch (no per-component file). Iconography documented as a
  foundation page (omits Variants/States/Theming per decision 19).
  RN renderer deferred to N+6.4 (F-ICON-RN-1). The first
  registry-based JS dispatch in Nuri — the co-pattern to decision
  37's attribute-dispatch for named-asset vocabularies.

## Frictions surfaced

- **Phosphor asset path differed from the brief**. The brief
  assumed `node_modules/@phosphor-icons/core/raw/`; the actual
  layout is `assets/{regular,bold,fill}/` with weight-suffixed
  filenames (`<name>-bold.svg`, `<name>-fill.svg`, plain
  `<name>.svg` for regular). The throwaway extraction script
  adjusted to walk the three weight directories. Low-impact —
  caught at extraction time, registry output unaffected.

- **`lead`-attribute double-decode created a stray `<nuri-icon>`**.
  The foundation page's `lead` text originally contained literal
  `<nuri-icon>` to name the element in prose. `nuri-page`
  interpolates `lead` raw into `innerHTML`; the attribute value
  HTML-decodes once on read, then `innerHTML` re-parses it,
  materialising a real nameless `<nuri-icon>` that logged
  `[NuriIcon] unknown name "null"`. First fix (`&lt;nuri-icon&gt;`)
  failed — the double-decode re-created the element. Resolved by
  rewording the lead to drop angle brackets ("shipped as the
  nuri-icon custom element"). Verified: 31/31 page icons named,
  0 empty, zero `[NuriIcon]` warnings. The deeper `nuri-page`
  raw-innerHTML-interpolation gotcha is a latent shell sharp edge,
  not specific to this page; left as-is (no other consumer hits it).

## Why iconography now (sequence position)

IconButton (N+6.4) and every downstream icon-consuming component
(SegmentedControl · ListItem · TabBar) need a working icon
primitive. Shipping IconButton first would force hand-rolling an
icon slot — a return to the kind of per-consumer improvisation
F-LAYOUT-1 captured for layout. Iconography is the **prerequisite
for any icon-bearing component**, which is what makes it the right
sequence position rather than a bridge after IconButton. The
operator chose to land it as N+6.3 (ahead of the originally-planned
N+7 Iconography slot, and ahead of the alternate N+6.3 Tag/
IconButton candidate) precisely because it unblocks the most
downstream work.

After N+6.3 closes, N+6.4 (IconButton) lands against:

- A working `<nuri-icon>` web element + the decision 38
  registry-dispatch pattern
- The deferred Icon RN renderer question (F-ICON-RN-1) — IconButton
  is the first consumer that forces it, so the RN renderer gets
  built against a concrete consumer rather than in the abstract
- The opportunity to add the Behavioural-delta section to the
  component template (R1 mitigation · n=2 confirmation point after
  Button)
