## The grounding correction

The brief's premise was "the accent system is already generic except ONE spot (`buildSemanticCascade`
hand-writes lilac's 5/6/6b)." Verifying against the tree found **four** accent-hardcoded spots, not one
— two emitters + two test oracles. The generify is the same shape in each: **loop the non-neutral
accents from the data** instead of naming lilac. Orange falls out; lilac stays byte-identical.

1. `scripts/parsers/semantic-css.js` · `buildSemanticCascade` — hand-wrote lilac blocks 5/6/6b.
2. `scripts/parsers/semantic.js` · `selectorMatches` — hand-coded `neutralOk`/`lilacOk`. **The
   latent bug**: an `[data-accent="orange"]` block has no `neutral`/`lilac` attr, so the old code
   returned `matches:true` for EVERY accent — orange (later in source order) would have clobbered
   lilac's resolution. Generified to match the accent named in the selector.
3. `scripts/parsers/colour-css.js` · the primitive emit — hand-wrote `setThemedScale(map,'lilac',…)`.
   The orange ramp must become `--nuri-color-orange-*` primitives (the cascade refs point at them).
4. The two test oracles (`colour-semantic.test.js` · `tokens-parser.test.js`) — pinned lilac.

## The mutation (proves the generify, not a hardcode)

Removing `orange` from the `accent` matrix + `ACCENTS` and rebuilding regenerates `tokens-semantic.css`
**identical to the pre-orange `main`** and `Accent` back to `'neutral' | 'lilac'` — orange vanishes
everywhere, lilac unchanged. (Reverted.) Orange lives ONLY in data: `colours.ts`, the CSS ramp block,
the `ACCENTS` entry, and the test oracles — no emitter names it.
