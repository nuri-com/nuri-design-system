# Session N+6.6 · Topbar · IconButton `fill` passthrough

**Status**: closed (2026-05-29)
**Type**: main sequence (the first compositional chrome shell · a
layout primitive that composes its content through named light-DOM
wrappers rather than enumerating use-cases · validates the Tabs
child-reparenting compound mechanism at a second consumer)

## Outcome

Two cohesive deliverables, the first composing the second:

1. **Topbar** ([`lib/components/topbar/`](../lib/components/topbar/))
   ships as `<nuri-topbar>` + `<nuri-topbar-start>` /
   `<nuri-topbar-end>` — the **first compositional chrome shell** and
   the **second light-DOM child-reparenting compound** (after Tabs).
   It is a three-region layout — `[leading] · children · [trailing]`
   — driven by a **single structural boolean, `center`**
   ([decision 46](../decisionlog.md#46-compositional-chrome-shell-via-named-light-dom-wrappers--n66)).
   The caller composes content into the named wrappers; everything
   else is the centre region. **Slots, not use-case variants** — no
   `variant="back"`, no `title`/`subtitle` prop. As a layout primitive
   its `@layer tokens` block is **empty** (no `--nuri-topbar-*`
   tokens · the [decision 37](../decisionlog.md#37-layout-primitives-consume-semantic-vocabulary-via-prop--no-component-token-aliasing--n62)
   pattern); all styling consumes semantic tokens directly and the
   pipeline skips its per-component emit.

2. **IconButton `fill` passthrough**
   ([`lib/components/icon-button/icon-button.js`](../lib/components/icon-button/icon-button.js))
   — `fill` joins `ATTRS` + `observedAttributes`; when present, `#sync`
   forwards `fill=''` to the inner `<nuri-icon>`, else removes it
   ([amendment 40.1](../decisionlog.md#401-amendment--n66--fill-weight-passthrough)).
   A **pure passthrough** — no new token, no layout change, the
   single-size lock (decision 40) unchanged. It is consumer-driven:
   Topbar's close affordance wants a filled `x-circle`, and routing
   the glyph weight through the existing IconButton wrapper keeps
   Topbar composing Icon **only** through IconButton — no new direct
   `<nuri-icon>` consumer enters the tree (preserves the F-ICON-RN-1
   single funnel).

**F-ICON-RN-1 was deliberately sidestepped a third session running** —
but its renderer direction was **refined** this session (see below).
Topbar composes Icon only through IconButton, so the direct-Icon
consumer count held at two and the renderer debt carried forward
unchanged, **not** advanced and **not** a partial renderer.

## API · operator-locked at session open

```
<nuri-topbar center>                     center: boolean · the ONLY prop
  <nuri-topbar-start> … </nuri-topbar-start>   leading region (display:contents wrapper)
  … centre content …                            anything outside the wrappers
  <nuri-topbar-end>   … </nuri-topbar-end>     trailing region (display:contents wrapper)
</nuri-topbar>
        center=false → left-aligned title · side regions flex:0 · centre flex:1 left
        center=true  → balanced title · side regions flex:1 · centre flex:0 centred
                       NO title/subtitle prop, NO variant enum, NO elevation/border knob,
                       NO Shadow DOM / <slot> · light-DOM reparenting only

<nuri-icon-button … fill>                fill: boolean · forwards filled weight to inner <nuri-icon>
                       single-size lock UNCHANGED · pure passthrough · no new token
```

## Decisions locked

- **[Decision 46](../decisionlog.md#46-compositional-chrome-shell-via-named-light-dom-wrappers--n66) ·
  Compositional chrome shell via named light-DOM wrappers · slots not
  use-case variants.** Topbar is a layout primitive: a three-region
  flex host (`height: size.xl` · `background: bg-canvas` ·
  `color: text-primary` · `gap: space.sm`) whose only prop is the
  structural `center` boolean. `connectedCallback` queries
  `:scope > nuri-topbar-start` / `nuri-topbar-end`, treats every other
  top-level node as centre content, builds three region `<div>`s, and
  reparents the children into them — the **same light-DOM mechanism as
  Tabs** (decision 43 · no Shadow DOM, no `<slot>`). Edge padding is
  **attribute-dispatched** (decision 42): JS sets `data-center` /
  `data-leading` / `data-trailing` on the host reporting *state*, CSS
  `@layer rules` selectors own *appearance* (center → `padding-inline:
  space.lg`; off-center occupied edge → `space.sm`; off-center empty
  edge → `space.lg`). `@layer tokens` is empty → no
  `build/components/topbar.ts`. Anti-scope: no `--nuri-topbar-*`
  tokens, no props beyond `center`, no Shadow DOM, no
  SegmentedControl, no Icon RN renderer.

- **[Amendment 40.1](../decisionlog.md#401-amendment--n66--fill-weight-passthrough) ·
  IconButton gains a `fill` weight passthrough.** `fill` boolean
  forwards to the inner `<nuri-icon>`'s filled weight; the
  single-size lock (the substance of decision 40) is unchanged. Pure
  passthrough · the weight resolves entirely inside Icon's existing
  registry dispatch (decision 38), exactly as a bare `<nuri-icon fill>`
  would. RN mirrors it as `fill?: boolean` on `IconButtonProps`, a
  no-op in the stub (RN Icon renderer deferred · F-ICON-RN-1).

## F-ICON-RN-1 · still OPEN (operator-deferred a third session · direction refined)

The Icon RN renderer was **operator-deferred again** this session.
Topbar composes its close/back/settings affordances through
**IconButton, not `<nuri-icon>` directly**, so the direct-Icon
consumer count held at two and the renderer debt carried forward
**unchanged** — IconButton stays the single funnel every glyph passes
through.

**No partial RN renderer shipped.** What *did* change is the renderer
direction, refined this session: when it lands, feed the **shared
registry's SVG string** into `react-native-svg`'s `SvgXml` and pair it
with a **typed `build/icons.ts`** emit from the pipeline — one
registry, two readers (web inline + RN `SvgXml`). Explicitly **not**
SVGR or per-glyph `<Path>` codegen, which would fork the glyph source
and break the single-registry invariant decision 38 rests on. The
refined trigger: the first direct `<nuri-icon>` consumer *outside*
IconButton, or the first real RN build — whichever comes first. The
debt stays surfaced in three places (RISKS.md F-ICON-RN-1, the
IconButton migration stub, IconButton's page Roadmap).

## Frictions surfaced

- **`nuri-text-title-sm` is not a real class.** The first topbar.html
  draft used `<h1 class="nuri-text-title-sm">` for region titles; a
  grep showed only `.nuri-text-muted` / `-on-inverse` / `-primary`
  exist as `nuri-text-*` helpers — the real type classes are
  `.nuri-type-{step}` / `--em`. Fixed by switching every title to
  `<nuri-typography size="md" emphasis>` and loading the typography
  component CSS/JS + `styles/typography.css` in the page head. Lesson:
  verify a utility class exists (grep the stylesheet) before composing
  against it.

- **`subtitle` rendered a live `<nuri-topbar>` element.** A center-demo
  `subtitle="&lt;nuri-topbar center&gt; · …"` was decoded by
  `<nuri-demo>` (demo.js inlines `subtitle` as **innerHTML**), so the
  decoded `<nuri-topbar center>` became a **real 9th topbar element**
  inside the demo card meta. Fixed by **double-escaping**
  (`&amp;lt;…&amp;gt;`) so the literal text displays. After reload: 8
  real bars, 0 strays. Lesson (same class as N+6.5's `lead`-attribute
  HTML injection): `<nuri-demo>`'s `subtitle` is an HTML sink, not a
  text sink — angle brackets must be double-escaped.

## Why Topbar now (sequence position)

N+6.5 shipped Tabs, the first light-DOM child-reparenting compound.
Topbar reuses that exact mechanism at a second consumer — proving the
pattern generalises from a stateful selection compound (Tabs) to a
stateless compositional shell (Topbar). It is also the natural place
to exercise IconButton's `fill` passthrough at a real consumer (the
filled close glyph) rather than minting the prop speculatively.

Deferring the Icon RN renderer a third time stays deliberate: Topbar
composes Icon **only through IconButton**, so it grows the
chrome/compositional surface without minting a new direct Icon
consumer or deepening the funnel. The session paid down a *different*
kind of debt — refining the renderer **direction** (SvgXml over the
shared registry · no per-glyph codegen) so the eventual
implementation slice starts from a locked approach.
