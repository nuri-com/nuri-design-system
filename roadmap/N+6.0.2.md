# Session N+6.0.2 · semantic.html dual-mode docs refactor · per-accent split + side-by-side themes

**Status**: closed (2026-05-28)
**Type**: bridge (docs surface parity · page + lib refactor)

## Outcome

`pages/foundations/colour/semantic.html` now documents the **full
resolution matrix** of every semantic token structurally instead of
interactively. The page used to render one mode + one accent at a
time, driven by `data-theme` (topbar) + an inline accent select
(page-local); a reader had to toggle two controls to reconstruct the
matrix
[decision 33](../decisionlog.md#33-semantic-token-docs--format-b-verbose-dual-mode-for-context-dependent-tokens--n601)
already documents at the CSS source. This session brings the docs
surface in line with the convention:

- **Sections** · 5 → 6. The previous single **Accent** section
  (with the inline select toggling neutral / lilac) splits into two
  structural sections — **Accent · neutral** + **Accent · lilac** —
  each rendered against its fixed accent context.
- **Tables** · 5 → 7 columns when the page opts in. DTCG · CSS var ·
  **Reference Light** · **Light** · **Reference Dark** · **Dark** ·
  Type, with both modes resolved in parallel against the section's
  accent. The reference IS one column per theme — the reference
  itself can change per theme (e.g. `var(--nuri-color-neutral-1-light)`
  → `var(--nuri-color-neutral-1-dark)` for the same
  `--nuri-bg-canvas`), so a single Reference column would lose half
  the matrix. The inline swatch chip moves from the DTCG name cell
  into each Reference cell — one chip per cascade context, carrying
  explicit `data-theme` + `data-accent` attrs so the chip renders
  the resolved colour for its own context (independent of the live
  `<html data-*>` state). Frozen lilac tokens (solid / solid-pressed
  / on-solid) show identical Reference Light = Reference Dark +
  identical chip colours, surfacing the P4 freeze directly in the
  data instead of through prose.
- **Widget removed** · the page-local accent select + its JS
  (`accentSelect.addEventListener`, `refreshAccentSelect`, the
  `NuriState.subscribe` on `accent`) are deleted. With both accents
  visible structurally, the widget's purpose is satisfied. The
  topbar theme toggle is no longer load-bearing for this page either
  — both columns always render.
- **Prose rewrite** · "How to read these tables" describes the
  per-accent section structure + the dual-value-column layout, drops
  the "toggle the theme switch" instruction, and cross-links
  [decision 33](../decisionlog.md#33-semantic-token-docs--format-b-verbose-dual-mode-for-context-dependent-tokens--n601)
  so a reader following the convention from the page to the CSS
  source finds the inline-comment counterpart at the canonical
  declaration block.
- **Set indicator simplified** · the `.nuri-token-meta` paragraph
  drops both `current-accent` (structural now) and `current-theme`
  (both modes shown always); it reads `Set · core`.
- **Roadmap** · the **Topbar accent control** item rewords to drop
  the "promote the inline select" framing (the select is gone), but
  the planned-state stays — a global topbar control still arrives
  when the second saturated accent ships.

The lib change is **strictly additive**.
[`lib/docs/tokens.js`](../lib/docs/tokens.js) `parseSemantics()`
gains a `bothThemes: true` option (populates
`referenceLight + referenceDark + valueLight + valueDark` against
the requested accent); `renderTable()` gains a `showBothModes: true`
option paired with `accent` (emits 7 columns + a chip inside each
Reference cell carrying its own `data-theme` + `data-accent`).
Existing default parameters / fields stay; new ones layer on top.
`primitive.html`, `button.html`, and `exploration.html` keep their
single-`Value` 5-col render with the chip in the DTCG name cell —
zero call-site change.

[Decision 20](../decisionlog.md#20-token-table-format-unified-across-every-page--n2)
gains an
[**amendment 20.1**](../decisionlog.md#201-amendment--n602)
locking the dual-value-column allowance. Trigger is dependency-
driven, identical to
[decision 33](../decisionlog.md#33-semantic-token-docs--format-b-verbose-dual-mode-for-context-dependent-tokens--n601):
a table emits one value column per varying-dimension value when the
page documents the matrix structurally; otherwise stays
single-`Value`. Future density / font dimensions extend the same
option family (`showAllDensities`, `showAllFonts`) when a page
chooses to document those dimensions structurally rather than
interactively. No new decision number; the amendment hangs off
decision 20 per the established pattern (precedents: 2.1, 7.1,
23.1, 27.1).

No CSS edits (`styles/tokens-semantic.css` is the surface Format B
already documents — this session changes only the page that READS
it). No new tokens, no new components, no new pages. `npm test`
stays 15/15; `npm run build` continues emitting 216 colour
primitives + 18 semantic × 2 accents × 2 themes;
`npx tsc -p docs/migration-tests/button-matrix/tsconfig.json`
exits 0.

## Why N+6.0.2 not N+6.1

Different domain · different audit surface.
[N+6.1](./index.md#whats-next--session-n61--semantic-sizing--spacing--button-refactor)
introduces new semantic spacing + sizing token families + their
foundation pages + the button.css full refactor to consume them +
emitter extension — ~10 ship items in the "new tokens land" mode.
N+6.0.2 is a single-page refactor + an additive lib change + an
amendment — 9 ship items in the "docs surface parity" mode. Bundling
mixes mental models inside one closeout audit. Sequencing keeps
each audit focused on one class of change. Mirrors the
[N+6.0.1 → N+6.1 sequencing rationale](./N+6.0.1.md#why-n601-not-bundled-with-n61):
docs-convention lock before code-landing so the next agent inherits
the surface parity by construction.

X.Y.Z numbering: N+6.0.2 is the second derivative of N+6.0's
primitive direct-pixel migration thread. N+6.0.1 locked the CSS-side
Format B convention; N+6.0.1.1 propagated the convention to the
spec-authoring skill surfaces; N+6.0.2 closes the loop on the
**docs-page** surface (the one that READS the CSS the previous
sessions documented). Three derivatives, one consistent
dependency-driven trigger, no new decision numbers — only an
amendment to the existing token-table-format decision.

## Post-audit operator polish

After audit close, operator noticed two related shortcomings in the
6-col draft that surfaced only with the dual chips visible side-by-
side: (1) the single Reference column showed only the light-mode
reference, losing half the matrix when the reference itself varies
per theme (`var(--nuri-color-neutral-1-light)` ↔
`var(--nuri-color-neutral-1-dark)` for the same `--nuri-bg-canvas`);
(2) the single chip in the DTCG name cell could not show both
modes' resolved colours and resolved against the live `<html data-*>`
state regardless of the section.

Polish applied (additive lib extension + page wiring, post-close):

- `parseSemantics({ bothThemes: true })` now populates
  `referenceLight + referenceDark` in addition to
  `valueLight + valueDark`. The light + dark walks run with the
  same `accent`, different themes.
- `renderTable({ showBothModes: true, accent })` now emits 7 columns
  (DTCG · CSS var · Reference Light · Light · Reference Dark · Dark
  · Type) and moves the inline swatch chip out of the DTCG name
  cell, replacing it with one chip per Reference cell. Each chip
  carries `data-theme="light|dark"` + (where applicable)
  `data-accent="<section accent>"` directly on its own
  `<span class="nuri-swatch nuri-swatch--xs">`, so the
  `style="background: var(...)"` resolves under that explicit
  cascade context — chrome chips render correctly under each theme,
  accent chips render correctly under each (theme × accent).
- A new `modeSwatchHTML(token, theme, accent)` helper sits alongside
  `inlineSwatchHTML(token)` in `lib/docs/tokens.js`. The two are
  mutually exclusive — one chip-in-name-cell layout per render
  call. Both reuse `.nuri-swatch--inline` (24px chip + negative
  `margin-left: calc(-1 * px-48 + px-6)`) so the dual-mode chips
  hang OUT of the Reference cell's content area into the padding
  gutter, mirroring the alignment primitive.html gets for free on
  its first-cell DTCG column. To make the math work on a non-first
  cell, the renderer adds an inline `style="padding-left: var(--nuri-px-48)"`
  on each Reference Light + Reference Dark `<th>` and `<td>` —
  reference TEXT then starts at exactly 48px from the cell border =
  aligned with the column-header edge, just as primitive's
  `color.neutral.1.light` aligns with its "DTCG" header. No CSS
  edits — only inline styles parameterised by existing primitive
  tokens.
- `semantic.html` passes `accent: 'neutral'` to chrome-section
  renders (irrelevant to the resolved colour but keeps the wrapper
  shape consistent) and the matching accent to each accent-section
  render.
- Decision 20.1 amendment + retrospective + roadmap/index.md Current
  state updated to describe 7 cols + dual chips + dual references
  (was 6 cols + single reference).
