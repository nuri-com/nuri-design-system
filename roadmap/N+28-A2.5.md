# Session N+28 · A2.5 · collapse the RN dual-version tree — NON-VIABLE **and** UNNECESSARY (finding)

**Status**: shipped on `chore/collapse-rn-dual-tree` as a **documented finding · doc-only · no lockfile/code change**. The session set out to collapse the orphaned dual-version RN tree (root `react@19.2.6` / `react-native@0.80.3`) once, deliberately, so the package-ADDING carves (A3+) would `npm install` churn-free. The investigation proved the collapse is **impossible in-place**, **non-viable via the only mechanism that works** (a full regen, which breaks the toolchain), **and — the sharpening finding — unnecessary** (a non-RN carve-add is conservative; the dual tree is a harmless vestige). Per the operator decision, this is **Option 2**: ship the finding, correct the false premise everywhere, leave the dual tree in place.
**Type**: a §9-independent infra precursor to A3 ([decision 68](../decisionlog.md) · Phase A). **NON-VISUAL** (lockfile / toolchain · no rendered surface · the proof is the gates + the probe diffs). Operator-directed throughout: the collapse mechanism was escalated and approved as a verify-then-revert experiment; a carve-add probe was added at the checkpoint to sharpen what Option 2 means for the carves.

## The premise that failed

The brief's plan step 1 — "`npm install` at the repo root → it collapses `0.80.3`→`0.81.5`" — and the memory lockfile-gotcha both assumed **a plain `npm install` collapses the dual tree on npm 10.8.2**. **It does not.** That belief was inferred from **A1's rename**: renaming a workspace (`@nuri/factory` → `@nuri/rn` · dir + name) changes the workspace set, which forces npm to rebuild the ideal tree from scratch — and *that rebuild* collapses (and, as A2.5 now shows, drifts). A1 dodged it with a mechanical lockfile string-rename. A **plain** `npm install` with nothing changed never rebuilds the ideal tree, so npm's conservative re-dedupe leaves the orphan exactly where M4 ([§65.11](../decisionlog.md)) found it — the M4 finding is **still true** on npm 10.8.2.

## In-place collapse is impossible — five attempts

| # | command | result |
|---|---|---|
| 1 | `npm install` | **no-op** ("up to date" · npm trusts the satisfiable lockfile · no ideal-tree rebuild) |
| 2 | `npm install --package-lock-only` | **no-op** (no orphan pruned) |
| 3 | `npm dedupe` (± the override) | **ERESOLVE** — wants to hoist `react-native@0.81.5` to root, but `jest-expo`'s `peer react-native@"*"` is currently satisfied by the orphan `0.80.3`; npm's strict peer resolver bails |
| 4 | `npm install --force` | **no-op** |
| 5 | `rm package-lock.json && npm install` | **re-serializes the existing `node_modules`** (orphan persists · npm rebuilds the lockfile *from the installed tree*, not a fresh resolution) |

The root `overrides: { react: "19.1.0", react-native: "0.81.5" }` (the M4 "option (b)", now unblocked) is **inert in-place**: npm 10.8.2 won't apply a newly-added override to a lockfile it already considers valid (attempts 1, 2, 4 all no-op with the override present). The orphan is **structural** — `react@19.2.6` + `react-native@0.80.3` + 8 `@react-native/*@0.80.3` sub-packages, re-hoisting across three locations — so the A1-style mechanical string-edit isn't safe here (A1 worked because a rename is a pure path substitution with no structural change).

**The only mechanism that applies the override and collapses is `rm -rf node_modules package-lock.json && npm install`** — a true from-scratch resolution. That is the brief's explicit anti-goal ("M4 found it broke jest-expo's lodash"). This was escalated to the operator, who approved running it as a **verified + revertible** experiment (the anti-goal forbade a *blind* regen; this is the verification it wanted, via the only mechanism that works).

## The verified regen — collapses, but a whole-tree refresh that breaks the toolchain

`rm -rf node_modules package-lock.json && npm install`, run **without** the override first (operator refinement: prefer dropping it — nothing declares the orphan, so a fresh resolve may pick single-version on its own):

- ✅ **It collapses cleanly, and the override is NOT needed.** `0.80.3` / `19.2.6`: **0 occurrences**. Single `node_modules/react-native@0.81.5` + `node_modules/react@19.1.0`, both hoisted to root; the nested `packages/{rn,expo-demo}/node_modules` copies dissolve into one physical copy each. Lockfile 12444 → 9526 lines.
- ❌ **But a fresh resolution re-resolves the ENTIRE tree to today's registry** — **63 transitive packages drift**, far beyond the RN collapse: `metro` + all `metro-*` `0.82.5 → 0.83.3` (and `metro@0.83` requires node ≥20.19.4; this env is node **20.19.3**), `@types/node 25 → 26`, `brace-expansion 1 → 5`, `commander 12 → 7`, `entities 6 → 4`, and **`node_modules/lodash` vanishes** (only `lodash.debounce` / `lodash.throttle` remain).
- ❌ **Canary fails:** `npm test -w @nuri/rn` won't even start — `jest-expo`'s preset resolution breaks (`Module jest-expo should have "jest-preset.js"…`), although `jest-expo@54.0.17` is present, intact (its `jest-preset.js` exists), and `require.resolve`-able from `packages/rn`. **This is the M4 breakage reproducing** — driven by the whole-tree drift, manifesting through `jest-expo` (and `lodash` disappearing), not a single missing file.

So the regen does **not** deliver a *targeted* collapse; it delivers a full dependency refresh that breaks the RN toolchain. **The whole-tree drift is the blocker — not the node version**: a node bump to 20.19.4 would clear the `metro@0.83` EBADENGINE warning but the regen would *still* be a 63-package whole-tree refresh, not the targeted RN collapse the brief wanted. Per the operator's gate-failure rule, the regen was **reverted**: `git checkout package-lock.json` (lockfile byte-identical to baseline) → `npm ci` (dual tree rebuilt) → `npm test -w @nuri/rn` **27/27 + 7 snapshots** green again.

## The sharpening probe — a carve-add is conservative (the dual tree is harmless)

The brief's Option-2 line "carves keep per-carve manual lockfile management (A1-style)" assumed an ADD collapses (untested). The carves (A3/A4/A5) add **non-RN, build-free web workspaces depending on `@nuri/spec` only** — unlike A1, which *renamed an RN package*. A throwaway stub workspace of exactly that shape (`packages/_carve-probe` · `dependencies: { "@nuri/spec": "*" }`) + `npm install`:

```
$ git diff --numstat package-lock.json   →   11  0  package-lock.json
```

The **entire** diff is the new workspace's two entries (the `node_modules/@nuri/_carve-probe` symlink + the `packages/_carve-probe` definition). **The RN tree is untouched** — zero `react-native` / `@react-native` / `react` lines; the orphan `0.80.3` stays (×29, baseline). Reverted (`rm -rf packages/_carve-probe` + `git checkout package-lock.json` + `npm install` to drop the stale symlink · lockfile == baseline).

**Conclusion: a non-RN workspace add stays conservative — npm only appends the new entry, never re-dedupes the RN tree.** The dual tree is a **benign vestige, not a carve-trap**.

## The finding (what Option 2 records)

| question | answer |
|---|---|
| In-place collapse on npm 10.8.2? | **Impossible** — 5 commands all no-op / ERESOLVE; the override is inert in-place |
| Why did A1 "collapse"? | A1 *renamed* a workspace → forced an ideal-tree rebuild. A plain/no-op install never rebuilds. |
| Deliberate collapse (the only mechanism = full regen) on node 20.19.3? | **Non-viable** — a fresh resolve is a whole-tree refresh (63 pkgs drift) that breaks `jest-expo` + drops `lodash` (the M4 breakage reproduces). The drift is the blocker, not node. |
| Override needed for the regen-collapse? | **No** — a fresh resolve collapses without it (nothing declares the orphan); and it's inert in-place anyway. |
| Does a carve (non-RN workspace add) collapse the tree? | **No** — conservative (+11 / −0 · RN tree untouched). |
| **Net** | The collapse is **non-viable AND unnecessary.** The dual tree is harmless; the carves just `npm install`. Only RN-package **structural** changes (the A1 rename) force a rebuild needing manual lockfile care. |
