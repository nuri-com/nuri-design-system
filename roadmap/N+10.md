## Outcome

The **Playground** is a SEPARATE docs area where real screen compositions render
live inside device frames — the surface that makes the agent-first loop's
"composes" step visible
([decision 21](../decisionlog.md#21-consumer-model--three-agent-personas--operator--n3)).
It validates the design system on a real layout (a wallet home screen) rather
than a component in isolation. It is chrome-only glue over existing components:
**no new component, token, or glyph** ships from the composition.

- **Area** ([`lib/playground/`](../lib/playground/) + [`pages/playground/`](../pages/playground/)) —
  a simpler sibling of the DS `<nuri-shell>`: no nav tree, no global token
  toggles. **`<nuri-playground-shell>`** builds a topbar + a body that is either
  a card grid (index) or a horizontal-scroll row of device-framed views
  (document). A **fixed light + cream surface** — the pages pin `<html
  data-theme="light" data-neutral="cream">` regardless of the shared docs
  localStorage (without `NuriState.set`, so DS prefs are untouched).
- **First document, My vault** ([`pages/playground/my-vault.html`](../pages/playground/my-vault.html)) —
  the wallet home screen, composed ENTIRELY from shipped components (Topbar ·
  Box · Stack · Typography · IconAvatar · IconButton · List · NavItem · Button ·
  TabBar · Icon) plus raw-HTML bits (balance rows · swap overlay · € total) that
  are the *missing-component candidates* this session LOGGED, not built.

## `<nuri-demo>` gains two opt-ins

- **`device` control** — the preview renders inside a phone device frame (bezel ·
  status bar · cutout · bottom control) and the toolbar shows a device picker.
  DS component pages never list it, so they are unaffected — the frame is purely
  additive.
- **`layout` prop** — `widget` (default · the DS docs card) | `board` (the
  playground panel: 560px, no radius, single right border, `height: 100%`,
  toolbar moved BETWEEN preview and code, the preview is the resizable region
  [`resize: vertical`, tall by default so the code starts below the fold and the
  user drags to reveal it], both panes scroll independently). `layout` reorders
  only the DOM section order (not CSS `order`, so reading / tab order stay
  correct).

## Device frames · 4 presets × 4 platform chrome kits

Each `DEVICE_OPTIONS` entry carries `value` (→ `data-device`, dimensions),
`font` (platform typeface), and `platform` (→ `data-platform`, chrome kit). The
**SCREEN owns the device's real logical dimensions** (`inline-size` = width ·
`aspect-ratio` = width/height); the black frame `fit-content`-wraps it and ADDS
the bezel as padding (`--nuri-device-bezel` sides · independent `-top`/`-bottom`)
— so the given dimensions are the screen's, never eaten by the bezel. A
`PLATFORM_CHROME` map composes three independent traits; the DOM is structurally
distinct per platform, so JS composes structure and CSS owns paint
([decision 42](../decisionlog.md#42-box-gains-background--radius-props--attribute-dispatch-surface-vocabulary--evidence-gated-promotion--n65)):

| device | screen | bezel (t·side·b) | frame/screen radius | platform | cutout | status | bottom |
|---|---|---|---|---|---|---|---|
| iPhone 17e | 390×844 | 10·10·10 | 50/40 | `ios` | Dynamic Island | iOS | gesture pill |
| iPhone SE | 375×667 | 75·10·75 | 50/4 | `ios-classic` | none | iOS | none |
| Pixel 8 | 412×915 | 10·10·10 | 50/40 | `pixel` | Dynamic Island | Android | gesture pill |
| Android | 360×800 | 10·10·30 | 30/20 | `android` | punch-hole | Android | 3 buttons |

Operator calls at the visual checkpoints: Pixel reads like a modern iPhone
(floating bar + pill · only the Android glyphs/typeface differ); generic Android
is the distinct one (punch-hole + 3 transparent buttons on a taller chin,
Samsung-style); the SE home button is off-screen, so it's just generous black
forehead/chin padding. Changing the device re-skins the chrome in place
(`_swapDeviceChrome`) WITHOUT rebuilding the viewport, so the live composition
keeps its element state.

## Scoped device theming

In device mode the controllable `<nuri-scope>` is moved INSIDE the frame and
wraps ONLY the phone screen, so the toolbar's theme / neutral / font controls
re-theme **just the device content**. The card chrome inherits the page's fixed
light+cream context (no wrapping scope); the code pane is **forced dark**
(`data-theme="dark"`); the device picker also drives the font. Non-device DS
cards are unchanged (one scope wraps the whole self-contained demo).

## Token-cascade fixes (the reusable, machine-checked part)

Making a NESTED scope re-resolve neutral and font exposed three `:root`-only
asymmetries; all move to the attribute-only form the theme/accent overrides
already use, so a scope anywhere re-themes its subtree:

- **`[data-neutral="…"]`** + **`[data-font="…"]`**
  ([`styles/tokens-primitive.css`](../styles/tokens-primitive.css)) drop the
  `:root` prefix — a scoped neutral/font change was a silent no-op before.
- **`tokens-semantic.css` block 1** gains **`[data-theme="light"]`**, mirroring
  the attribute-only `[data-theme="dark"]` block 2 — without it a nested
  `mode="light"` scope could not re-declare chrome tokens (frozen at the PAGE
  neutral), so scoped neutral worked in dark but was a no-op in light. Light and
  dark are now symmetric.
- **A themeable scope carries `accent` alongside `theme`.** The accent×theme
  tokens use a compound selector (`[data-accent="lilac"][data-theme="dark"]`); a
  scope that flips `data-theme` matches the bare `[data-theme="dark"]` rule
  (resetting accent to neutral-dark), so without `data-accent` on the same
  element the lilac-dark override never matches and the brand reverts to neutral
  in dark. `<nuri-demo>` seeds `accent` from the page default whenever the scope
  carries `theme`.

**Pipeline parity** — `primitiveSelectorMatches`
([`pipeline/parsers/semantic.js`](../pipeline/parsers/semantic.js)) accepts the
bare `[data-neutral="…"]` form so the build still resolves its single chosen
neutral scope ([decision 31](../decisionlog.md#31-default-neutral-scale--cream--cli-parameter---neutral=scale--n58)).
Test 7 (`resolveSemanticCrossProduct`) caught the regression before ship.

## Playground topbar · the DS `<nuri-topbar center>`

The playground shell chrome uses the DS
[Topbar](../decisionlog.md#46-compositional-chrome-shell-via-named-light-dom-wrappers--n66)
(`center`): a leading **ghost** `caret-left` icon-button (documents only · back
to the index), a centre **`<nuri-typography size="sm" emphasis>`** title, a
trailing **soft `sm`** "Design system" button (text only, no arrow). The DS
button / icon-button are native `<button>`s (no `href`), so navigation is wired
with click→`location.assign` listeners on the host elements (the click bubbles;
the `data-pg-nav` attribute survives the topbar reparent). The bespoke
`.nuri-pg__topbar-*` / brand / back / ds-link CSS is retired; `.nuri-pg__topbar`
keeps only `position: sticky` + the divider.

## Anti-scope (held)

- **No new component, token, or glyph** from the composition. My vault is
  existing parts; the device-frame chrome is decorative inline SVG (the same
  category as the original status-bar glyphs).
- **The device frame is the playground's, not the DS's** — `device` is opt-in;
  no DS page lists it; dimensions/chrome are `--nuri-device-*` custom props on
  the frame, not semantic tokens. No pipeline COMPONENTS change, no `build/`
  emit change.
- **No `position: fixed` / routing** in the playground shell — a docs surface,
  not an app.

## Frictions

- **No new friction codes minted.** The cross-cutting work was cascade-symmetry
  repair (neutral/font/light attribute-only · accent-with-theme), not a new
  web↔RN gap.
- The token-cascade fixes are web-preview-only (the build resolves one fixed
  scope · decision 31), so they do not cross the RN boundary; the parser parity
  fix keeps the build green.
