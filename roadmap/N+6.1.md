## Frictions surfaced

**Consumer-side static-vs-dynamic split** · The TokenPath
auto-promotion (decision 34) + runtime-set exposure (decision 36)
combine to make `button.minHeight` no longer a literal number at
module load. `StyleSheet.create` evaluates before any
(theme × accent) context exists, so two of Button's seven
component-token fields had to move out of the static block into
the render-time inline style array. **Flagged as natural
consequence, not as a friction to mitigate.** The migration-test
pair documents the split honestly as the consumer-side reference
shape; production consumers (Unistyles dynamic style functions,
custom Context theme selectors) handle it more elegantly. A
consumer that prefers everything-static can opt the set into
`{ runtime: false, pipelineInline: true }` policy, but then the
vocabulary stops being part of the runtime contract — defeating
the point of exposing the layer.

**Type-classification overlap · primitive border-width vs
chrome semantic border colour** · Both families share the
`--nuri-border-` prefix. The pipeline-side `primitive.js`
`TYPE_PREFIXES` maps `--nuri-border-` → `dimension` (correctly,
for the primitive layer); the semantic-side runtime emitter
needed an explicit carve-out so `--nuri-border-subtle` /
`--nuri-border-default` / `--nuri-border-strong` (chrome colour
tokens) don't get mis-classified as dimensions and trigger the
"cannot convert '#dddac9' to a JS numeric expression" throw at
emit time. Fix: `semanticLeafTsType(cssVar)` has a single regex
carve-out for the three border colour names — mirrors the
specific-before-general ordering in
[`lib/docs/tokens.js`](../lib/docs/tokens.js) `TYPE_PREFIXES`
(where the same overlap is handled with
`/^--nuri-border-(subtle|default|strong)/` BEFORE the generic
`/^--nuri-border-/`). Surfaced + fixed in pass; no follow-up.

**Test-suite oracle update** · Three tests needed updates after
the auto-promotion:
- Test 7 (resolveSemanticCrossProduct oracle) gained 14 new
  entries — the SEMANTIC_EXPECTED table is exhaustive both ways
  (oracle ⊆ parser AND parser ⊆ oracle), so the new tokens
  break test 7 even though their values are trivial.
- Test 12 (every semantic var lands in tokens.ts) needed regex
  generalisation — the existing `\\b${leafName}:\\s+'` pattern
  assumed bare-identifier keys with string values, and didn't
  match `'2xs': 2,` (quoted T-shirt key, numeric value). The
  generalised pattern accepts either key shape and either value
  shape.
- Test 16 (per-component button.ts) needed
  `expectedLiterals` → `expectedPaths` migration for
  `minHeight` + `paddingX`; the `resolveComponentValue`
  deep-equal checks at the bottom also got two new asserts
  (`paddingX → tokenPath` + `radius → literal`).

This is the cost of test exhaustiveness — a feature, not a
friction. The tests caught the auto-promotion + the leaf-quoting
+ the leaf-type emit; an under-specified test suite would have
let any of those silently mis-emit.

## Why N+6.1 not N+6.2

N+6.2 (layout primitives Stack / HStack / VStack) **consumes**
the semantic dimension vocabulary that N+6.1 introduces. Without
N+6.1 first, Stack would have no `--nuri-space-*` to dispatch to
via its `gap` prop — the layout primitive would either consume
primitives directly (forcing the P3 carve-out decision before the
vocabulary stabilises) or carry its own ad-hoc T-shirt scale
inside the component (drift surface). Sequencing matters
structurally.

Bundling layout primitives with the semantic vocabulary would
also blur the closeout audit: a single combined session can't
disambiguate "is the vocabulary right" from "is the layout
primitive API right". The N+6.1 audit reads the vocabulary
choices in isolation; the N+6.2 audit will read the
layout-primitive choices against an already-locked vocabulary.

After N+6.1 closes, **N+6.2** lands the layout primitives
against:
- Existing semantic dimension vocabulary (operator-locked here).
- Existing per-component file pattern + TokenPath union
  (decision 34 · N+6.0.3).
- The migration-test consumer pattern this session established
  (static-vs-dynamic split as the reference shape).
- The Open question on P3 mechanical enforcement (which N+6.2's
  primitive-consumption pattern resolves one way or the other).
