# Session N+6.0 · Primitive rename + value migration · `--nuri-size-N` → `--nuri-px-N` direct-pixel scale

**Status**: closed (2026-05-28)
**Type**: bridge (primitive rename · pre-semantic layer)

## Outcome

The primitive dimension scale moves from indexed (`--nuri-size-{0..12}`,
where `size-3 = 8px` and `size-12 = 80px` are opaque mappings) to
**direct-pixel** naming (`--nuri-px-N`, where N is literally the
pixel value). Eleven values ship — `--nuri-px-{2, 4, 6, 12, 18,
24, 28, 36, 48, 60, 72}` — each consumed by at least one site post-
migration (per [P11](../pages/principles.html#p11-parsimony) +
[decision 30](../decisionlog.md#30-primitive-parsimony--no-speculative-additions--n571)).
Two hardcoded touch-target escapes (44px × 3 in `styles/shell.css`,
56px × 1 in `lib/components/button/button.css`) consume the new
scale via `var(--nuri-px-48)` and `var(--nuri-px-60)` respectively.

[Decision 32](../decisionlog.md#32-primitive-scale-uses-direct-pixel-naming---nuri-px-n--n60)
locks the naming convention + the full migration mapping table.
The `--nuri-size-*` prefix is reserved for the **semantic** sizing
layer arriving in N+6.1 (`--nuri-size-{xs, sm, md, lg, xl, 2xl,
3xl}`); both parsers' `TYPE_PREFIXES` tables keep a defensive
`--nuri-size-` entry so semantic-layer dimensions classify
correctly at the moment they land.

`--nuri-px-90` is intentionally **withheld** from this session's
primitive set — it lands in N+6.1 with the `--nuri-size-3xl`
semantic consumer. Pre-shipping under speculation would violate
the parsimony lock.

Inherits the N+5.7.1 parsimony lock — the FIXED anti-goal default
in [`prompts/working-session.md`](../prompts/working-session.md)
fired automatically; no speculative additions landed beyond the
11 consumer-justified primitives.

`npm test` is 15/15; `npm run build` continues to emit 216 colour
primitives + 18 semantic × 2 accents × 2 themes (counts unchanged
— this session touched only the dimension scale, never the colour
or semantic layers).

- **None new.** The migration was mechanically straightforward
  (sed with longest-prefix-first ordering). The single non-trivial
  arithmetic update was the `.nuri-swatch--inline` layout-math
  comment block at `styles/shell.css:765-783` — the new chip
  margin-left math is `-px-48 + px-6 = -42px` (was `-size-10 +
  size-3 = -40px`), and the resulting `token name starts at … =
  48px from cell border` invariant still holds because the
  margin-right shift (`size-5 → px-18`, i.e., 16→18) absorbs the
  margin-left shift (`size-3 → px-6`, i.e., 8→6) within the same
  cell-padding-left of 48. The arithmetic check is documented
  inline in the updated comment.
- F-TOKEN-1 (semantic-cascade pipeline) stays retired.
  F-LAYOUT-1 is still the highest-friction missing surface and is
  expected to start in N+6.2 (Stack/HStack/VStack) after N+6.1

## Why N+6.0 not bundled with N+6.1

Two reasons:

1. **Blast radius.** This session touched ~150 var() consumers
   plus the primitive declarations and the docs surfaces that
   describe the scale. Bundling the semantic layer (14 new
   declarations) + 2 new foundation pages + the button.css
   semantic refactor + the emitter extension would push to
   ~300 lines + new files in one session — outside the pattern
   threshold and would have made the closeout audit ambiguous
   ("are visual diffs from the rename or the semantic mapping?").
2. **Pattern.** Max ~5 deliverables per session; this one has
   ~10 already from the multi-file sweep nature. N+6.1 will have
   another ~10. Sequencing keeps each session's audit focused.

After N+6.0 closes, N+6.1 starts from a primitive layer with
direct-pixel names. The semantic layer maps cleanly:
`--nuri-space-sm: var(--nuri-px-6)` reads transparently against
the primitive value.
